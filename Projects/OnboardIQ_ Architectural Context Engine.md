# OnboardIQ: Architectural Context Engine
**Status:** hypothesis-set | **Hook:** Stop explaining your component library. Let it explain itself.

## 1. Foundation Hypothesis
**Universal Problem:** A company's component library is the most valuable piece of institutional knowledge its frontend team has built — and it's almost entirely inaccessible to new engineers. Storybook is incomplete or out of date. Confluence docs reference component names that were renamed two quarters ago. The codebase has 4 different implementations of the same pattern, and a new engineer has no way to know which one is canonical. The only reliable source of truth is a senior engineer, and senior engineers are fielding the same 'where is the pattern for X?' questions on repeat, draining their time and creating a bottleneck that gets worse as the team grows. ## 2. Unfair Advantage
**Capability:** OnboardIQ can be built on top of existing documentation sources — Storybook, Zeroheight, Notion, Confluence, GitHub — without requiring teams to create new documentation. The ingestion pipeline treats the component library itself (component APIs, prop types, usage examples in the codebase) as the primary source of truth, with documentation as supplemental context. A RAG pipeline over this structured knowledge base produces answers that are specific, source-cited, and linked to canonical implementations rather than generic best-practice suggestions. The IDE integration (VS Code extension) creates a zero-friction query surface: engineers ask questions inline while writing code, without leaving their working context.
**Motivation:** The cost of slow onboarding is quantifiable in a way that most DevX tools are not. A mid-level frontend engineer at $150K/year fully loaded costs approximately $12.5K/month. If the average time to first productive commit is 9 days and OnboardIQ cuts that to 3 days, that's 6 days × $625/day = $3,750 recovered per hire — before accounting for the senior engineer time freed from answering repetitive questions. At 10 hires/year, that's $37,500 in direct cost recovery plus hundreds of hours of senior engineer time returned to product work. The ROI story writes itself for any engineering lead who has sat through a quarterly headcount review.
**Insight:** Every company's component library already contains all the information a new engineer needs — it's just not queryable. The architecture is in the code. The reasoning is in the ADRs. The patterns are in the canonical usage examples. What doesn't exist is a layer that extracts this structured knowledge and makes it answerable in natural language, specific to this team's exact library. Generic AI tools fail here for the same reason generic docs fail: they don't know your library's specific component hierarchy, naming conventions, or usage constraints. OnboardIQ's moat is the schema it builds from your library — not just embeddings of documentation, but a structured graph of component relationships, pattern dependencies, and usage constraints that makes answers specific enough to actually use.

## 3. Principles
- Specificity over generality — always return the exact component, variant, and file path, never a category or a guess
- Source-first — every answer must cite its source (Storybook page, ADR, canonical usage example) so engineers can verify and learn the reasoning, not just copy the output
- No confident hallucination — if the answer isn't in the indexed library, say so explicitly and suggest where to look next, rather than synthesizing a plausible-sounding but unverifiable response
- Integrate where engineers already work — IDE extension, Slack bot, GitHub PR comment; the query surface must have zero-friction access, not require a context switch to a separate app
- Measure velocity, not volume — the product's north star is engineer time-to-first-productive-commit, not query count; optimize everything for that outcome

## 4. The Click Test
**Riskiest Assumption:** New engineers will trust OnboardIQ's answers enough to act on them without asking a colleague to verify — because a single confidently-wrong answer (wrong component, deprecated pattern, incorrect usage) will break trust immediately and cause engineers to revert to asking humans. The precision bar for OnboardIQ is higher than for a general-purpose AI tool: a new engineer has no baseline to evaluate whether the answer is correct, so errors are invisible until they cause a PR rejection.
**Test Method:** Shadow mode trial with 3 new engineers during their first 4 weeks. Deploy OnboardIQ alongside the existing onboarding process — no changes to docs, no reduction in Slack access. Log every query and result. After each session, prompt the engineer to rate the answer: 'Was this answer directly applicable to your task?' (yes/no/partially). Track: (1) answer helpfulness rate, (2) follow-up question rate as a proxy for answer completeness, (3) time to first PR submitted, (4) time to first PR merged. Compare against the previous 3-engineer cohort's baseline metrics.
**Success Metric:** 80% of answers rated 'directly applicable' by engineers during the 4-week trial. Time-to-first-PR reduces by at least 30% vs. the previous cohort's average. At least 2 of 3 trial engineers replace at least one Slack 'how do I?' question with an OnboardIQ query in week 1. Zero instances of OnboardIQ confidently recommending a deprecated or incorrect pattern (tracked via PR review feedback).
